# 安全模型与风险评估

> **本文档不是免责声明，是实测数据和具体风险。**

---

## 一、本项目没有隔离

```
虚拟机方案（VMOS / VPhoneOS / 光速虚拟机）
    32位应用 → 虚拟机 → 隔离层 → 宿主系统
    性能损失 60-80%，但出事只需删虚拟机

本项目
    32位应用 → 直接跑在系统里，和普通应用同级
    性能损失 20-40%，零隔离
```

**32 位应用获得的权限、能访问的目录、能调用的系统服务，与 64 位应用完全相同。**

---

## 二、老应用 = 全权限（最严重的风险）

### 机制

Android 6.0（API 23）引入了运行时权限。在此之前，**权限在安装时一次性全给**。

对 `targetSdk < 23` 的应用，系统仍使用旧模型：

```
targetSdk < 23  →  安装即获得所有 AndroidManifest 里声明的权限
                   用户不会被询问任何一次
                   pm revoke 无效（实测）
```

### 实测数据

装了一个 2016 年的音乐播放器（`targetSdk=22`），自动获得：

```
⚠ SEND_SMS                     发短信 —— 可扣费、可自我传播
⚠ RECORD_AUDIO                 录音
⚠ CAMERA                       拍照
⚠ ACCESS_FINE_LOCATION         精确定位
⚠ ACCESS_BACKGROUND_LOCATION   后台持续定位
⚠ READ_PHONE_STATE             读 IMEI/设备信息
⚠ ACCESS_MEDIA_LOCATION        读照片的拍摄位置（可反推住址）
⚠ READ/WRITE_EXTERNAL_STORAGE  读写全部存储
```

**全部是 `granted=true`，用户全程无感知。**

### 为什么 `pm revoke` 无效

```sh
$ pm revoke com.example.app android.permission.SEND_SMS
ok                                        ← 命令返回成功

$ dumpsys package com.example.app | grep SEND_SMS
android.permission.SEND_SMS: granted=true  ← 实际没变
```

对 targetSdk < 23 的应用，权限是"安装时全量授予"的，运行时撤销不生效。
**唯一的可靠办法是卸载。**

## 三、来源不可验证

从论坛、网盘、第三方 APK 站下载的老应用：

| 风险 | 说明 |
|---|---|
| **签名无法验证** | 无法确认是官方原版，还是被注入/重打包的版本 |
| **无哈希比对** | 官方早停更，没有可信的校验基准 |
| **可能已被下架** | 很多应用因恶意行为被 Play Store 移除，但 APK 仍在流传 |
| **加固/壳** | 老应用的加固壳可能有已知漏洞 |

**本项目的做法**：只从原始固件提取系统组件（可信），不提供任何 APK。

---

## 四、为什么不提供二进制

本仓库**不包含**：

- 32 位系统库（OPPO 版权）
- GPU 驱动（Qualcomm 版权）
- `tango_translator`（Amanieu Systems 商业软件）
- 任何 APK

**理由**：
1. 版权 —— 这些是厂商专有二进制
2. 安全 —— 无法保证转载的二进制未被篡改
3. 可持续 —— 读者应自己从官方固件提取，保证来源可信

## 五、风险评估表

| 场景 | 风险等级 | 说明 |
|---|---|---|
| 使用自己从官方固件提取的组件 | 🟢 低 | 来源可验证 |
| 运行 targetSdk ≥ 23 的应用 | 🟢 低 | 有运行时权限控制 |
| 运行 targetSdk < 23 的可信应用 | 🟡 中 | 权限全开，但应用本身可信 |
| 运行 targetSdk < 23 的**不可信**应用 | 🔴 **高** | 全权限 + 无隔离 + 来源不明 |
| 把本方案做成面向普通用户的产品 | 🔴 **高** | 需要额外做隔离层 |

## 六、如果要真正做成产品，缺什么

```
现状：原生执行，无隔离
    ↓ 需要补
1. 应用沙箱      限制文件访问、网络访问、IPC
2. 权限重映射    targetSdk<23 的应用强制降权
3. 网络隔离      可选的出站白名单
4. 完整性校验    APK 签名白名单
5. 崩溃隔离      单个应用崩溃不影响系统
```

**这正是虚拟机方案存在的理由。** 本项目的定位是**技术研究**，不是产品。

---

## 七、给读者的建议

1. **不要用主力机做实验** —— 用备用机
2. **先做完整备份** —— 至少备份 `/data/adb/modules`
3. **只跑自己信任的应用** —— 尤其是 targetSdk < 23 的
4. **装完立刻检查权限** —— `dumpsys package <pkg> | grep granted`
5. **不用的应用立刻卸载** —— 不要"留着以后可能用"
6. **生产环境请用虚拟机方案** —— 性能差但安全
